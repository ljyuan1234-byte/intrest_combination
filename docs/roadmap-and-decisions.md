# 路线图与决策记录

版本：V0.2  
当前阶段：文档优先，暂停新增功能开发。

## 1. 阶段路线图

### Phase 0：文档和架构冻结

目标：明确边界，形成可执行规范。

验收：

- 产品范围、领域模型和 Agent 权限完成评审。
- 敏感数据和删除策略明确。
- MVP 页面、接口和数据表可以从文档拆出任务。
- 所有高风险能力有明确的后置条件。

### Phase 1：基础平台

目标：账号、数据隔离、通知、数据库和文件上传基础稳定。

不接入模型和第三方账号，先打通内部数据闭环。

### Phase 2：核心生活模块

目标：待办/日程、健康记录、手动记账和首页概览可用。

### Phase 3：受控 Agent

目标：只读查询、建议卡片、结构化输出、审计和成本控制可用。

### Phase 4：Mini App

目标：娱乐/传统文化工具和内置容器稳定，票务只做入口或公开信息提醒。

### Phase 5：外部连接器

目标：在逐项安全、授权和条款评估后接入外部服务。

## 2. 文档到开发的拆解顺序

1. 从产品需求拆用户故事和验收标准。
2. 从领域模型拆数据库实体和领域服务。
3. 从 Agent 规范拆工具白名单和测试集。
4. 从数据治理拆权限、日志和删除任务。
5. 从路线图拆迭代任务，不跨阶段提前实现高风险功能。

## 3. 架构决策记录

### ADR-001：采用模块化单体

- 决策：首期一个 API、一个 Worker、一个数据库和一个 Web/Android 客户端体系。
- 原因：个人开发成本低，调试和部署简单。
- 代价：后续需要按照模块边界逐步拆分。

### ADR-002：Agent 不直接访问数据库

- 决策：Agent 只能调用注册工具，由领域服务执行查询和规则。
- 原因：避免越权、幻觉 SQL、敏感数据泄露和不可审计操作。

### ADR-003：写操作默认需要审批

- 决策：Agent 首期只读和建议；草稿和写操作区分，最终写入需用户确认。
- 原因：生活、健康、财务和票务数据都有真实影响。

### ADR-004：健康数据首期手动或上传

- 决策：不接入手机健康平台或穿戴设备自动同步。
- 原因：降低平台适配、隐私和数据质量复杂度，先验证建议是否有价值。

### ADR-005：财务首期只做手动记账

- 决策：暂不接入支付账户和账单自动同步。
- 原因：减少敏感凭据和第三方接口风险，先完成记录与分析闭环。

### ADR-006：抢票后置且独立建设

- 决策：首期只预留模型和入口，后续从官方信息查询开始。
- 原因：票务自动化涉及账号、验证码、风控、支付、服务条款和高并发风险，不能混入普通 Agent。

### ADR-007：票务操作在用户设备执行

- 决策：网页和 Android 的票务页面辅助操作由用户设备上的本地 Runner 执行；云端只负责配置、状态、通知和审批。
- 目标平台：12306，以及大麦等演出平台。
- 原因：避免云端代管登录态和远程控制设备；便于用户在关键步骤接管操作。
- 约束：每个平台分别实现适配器，不读取 Cookie、Token、密码库或系统凭据，不绕过验证码、风控和支付保护。

## 4. 待决策清单

- Android 最低支持版本。
- 健康建议是否需要身高、体重、年龄、目标、忌口和过敏源。
- 饮食建议的具体输出模板和免责声明。
- 普通锻炼建议与高强度训练计划是否分开。
- 后续票务优先支持铁路、演出还是其他场景。
- 12306 Web/Android 和大麦 Web/Android 的具体兼容性、服务条款和自动化许可。
- 本地 Runner 采用浏览器扩展、本地桌面程序、Android Accessibility Service 还是平台允许的测试自动化能力。
- 云端部署供应商、模型供应商和数据保留天数。

## 5. 变更评审问题

每次修改范围或架构前回答：

1. 这是 P0、P1 还是 P2 能力？
2. 是否增加新的敏感数据或外部授权？
3. 是否提升了 Agent 的风险等级？
4. 是否需要新增审批、审计、限流或回滚？
5. 是否能在不破坏当前领域边界的情况下实现？
